## 5. Проверки формы

Два уровня проверки:

| Уровень | Что проверяет | Где реализовано |
| --- | --- | --- |
| HTML Constraint Validation | `required`, `min="1"`, `step="1"`, `maxlength="100"` | `index.html` |
| Прикладная проверка | Положительное безопасное целое `id`, уникальность `id` в режиме создания, `trim` и длина названия 1–100, приоритет `low` / `medium` / `high`, наличие редактируемой задачи | `validateTaskDraft` |

Правила реализации:

- в режиме создания `id` преобразуется через `Number`; пустая строка не принимается как ноль;
- в режиме редактирования поле `id` заблокировано (`disabled`) и в `FormData` не попадает (`formData.get("id")` возвращает `null`), поэтому используется `editingId`;
- несколько независимых ошибок возвращаются вместе в объекте `errors`;
- ошибки показываются рядом с полем (`aria-invalid`, текст в `data-error-for`) и очищаются при событии `input` для соответствующего поля через `setCustomValidity("")`;
- после ошибки данные и хранилище не изменяются, запись не создаётся.

## 8. Восстановление данных и ошибки хранилища

| Состояние хранилища | `ok` | `source` | Результат в приложении |
| --- | --- | --- | --- |
| Ключ отсутствует | `true` | `initial` | Копия исходного набора, статус «Используется исходный набор; сохранённых данных пока нет.» |
| Корректная запись `{ version: 1, tasks }` | `true` | `storage` | Данные восстановлены, статус «Данные восстановлены из localStorage.» |
| Повреждённый JSON (`{broken-json`) | `false` | `fallback` | Исходный набор и предупреждение (`is-warning`) |
| Неизвестная версия схемы | `false` | `fallback` | Исходный набор и предупреждение |
| Некорректные задачи (неверные поля, дубли id) | `false` | `fallback` | Исходный набор и предупреждение |

Повреждённая запись автоматически не удаляется, её можно исследовать в DevTools и затем удалить кнопкой сброса. Исключения `getItem`, `setItem`, `removeItem` перехватываются внутри `task-storage.js`. Если запись не удалась, изменение остаётся в памяти вкладки, а пользователь получает предупреждение. Сброс удаляет только свой `storageKey` через `removeItem`, `localStorage.clear()` не используется. Ключи общего и индивидуального наборов разделены: `tip-js-practice-04:demo` и `tip-js-practice-04:variant`; проверки используют `tip-js-practice-04:checks:*`.

## 10. Собственные проверки

### Случай 1. Граница длины названия

- **Исходное состояние:** общий набор после сброса (4 задачи).
- **Действия:** ввести `id = 30` и название из 101 символа, отправить форму; затем исправить название на 100 символов и отправить снова. Значение подставлялось программно, так как `maxlength` ограничивает только ручной ввод.
- **Ожидание:** 101 символ отклоняется прикладной проверкой, 100 принимается.
- **Фактический результат:** при 101 символе ошибка «Название не должно быть длиннее 100 символов.», в списке осталось 4 задачи. При 100 символах задача добавлена (5 задач), длина названия в хранилище равна 100.
- **Итог:** пройден. Показывает, что нативного `maxlength` недостаточно и прикладная проверка нужна.

### Случай 2. Восстановление отредактированной задачи после перезагрузки

- **Исходное состояние:** общий набор после сброса.
- **Действия:** нажать «Изменить» у задачи `10` (она выполнена), заменить название на «Оформить итоговый README», сохранить, перезагрузить страницу.
- **Ожидание:** после перезагрузки сохранено новое название, статус «Выполнена» не сброшен.
- **Фактический результат:** название «Оформить итоговый README», статус «Выполнена», строка состояния «Данные восстановлены из localStorage.»

### Случай 3. Повторяющиеся id в сохранённых данных

- **Исходное состояние:** в ключ `tip-js-practice-04:demo` вручную записана корректная по синтаксису запись `version: 1` с двумя задачами с одинаковым `id = 1`.
- **Действия:** обновить страницу.
- **Ожидание:** запись отклоняется целиком, запускается исходный набор с предупреждением, повреждённая запись автоматически не удаляется.
- **Фактический результат:** видимые id: 1, 4, 7, 10; статус с классом `is-warning`: «Сохранённые данные не соответствуют схеме; используется исходный набор.»; запись в `localStorage` осталась без изменений. После кнопки сброса ключ удалён.

## 14. Вывод

В работе реализованы создание и редактирование задач через одну форму, два уровня проверки ввода (HTML Constraint Validation и чистая прикладная функция `validateTaskDraft`) и сохранение состояния в `localStorage` в формате `{ version, tasks }` с проверкой схемы при чтении. Нативная проверка быстро отсекает структурно неверный ввод, но не знает правил модели (пробелы в названии, дубликат `id`), поэтому прикладная валидация необходима. Успешный `JSON.parse` не доказывает корректность данных, поэтому полная проверка схемы выполняется до использования записи, а при любой ошибке применяется независимая копия исходного набора с предупреждением. Модули разделены по ответственности: сервис, валидация и хранилище не зависят от DOM, `renderApp` не пишет в хранилище, а ключи наборов и проверок разделены.
