## 1. Цель работы

Освоить подключение браузерного приложения к HTTP API: расширить клиентский модуль методами POST, PATCH и DELETE, реализовать доменный слой с проверкой ответов по контракту, построить интерфейс с состояниями `loading`, `ready`, `empty` и `error`, выполнить создание, редактирование, смену статуса и удаление задач через API и защитить интерфейс от устаревших ответов. Результат: приложение «Задачи из учебного API» работает с сервером, все автоматизированные и браузерные проверки пройдены.

## 3. Реализация

### 3.1. HTTP-клиент

Файл `src/api-client.js`. За основу взято решение ПР5, добавлены методы изменения данных.

- **`buildUrl`.** Проверяет `baseUrl` (абсолютный `http`/`https`, без query и hash), соединяет его с путём без двойного слеша и добавляет query через `URLSearchParams`. Пропускаются только `undefined`, `null` и `""`, значения `false` и `0` сохраняются. Входной объект `query` не изменяется.
- **Методы.** `requestJson` принимает `GET`, `POST`, `PATCH` и `DELETE` (регистр не важен). Любой другой метод вызывает `TypeError`. `body` у `GET` запрещён и тоже вызывает `TypeError`.
- **JSON-тело.** Если `body` передан, он сериализуется через `JSON.stringify` и добавляется `Content-Type: application/json`. Без тела заголовок `Content-Type` не отправляется. Заголовок `Accept: application/json` отправляется всегда.
- **Порядок разбора ответа.** Сначала проверяется `response.ok`: HTTP-ошибка превращается в `ApiError` с `kind: "http"`, а поля `status`, `code`, `details` берутся из `payload.error`. Это происходит раньше проверки `Content-Type`, поэтому ответ `502` с `text/plain` остаётся HTTP-ошибкой. Затем статус `204` возвращает `null` без чтения тела. Для остальных успешных ответов проверяется `Content-Type` и разбирается JSON, сбой даёт `invalid-response`.
- **Тайм-аут.** `AbortSignal.timeout(timeoutMs)`, по умолчанию 3000 мс; при срабатывании `kind: "timeout"`.
- **Отмена.** Внешний `signal` объединяется с тайм-аутом через `AbortSignal.any`. Причина сигнала отличает `aborted` от `timeout`.
- **Виды ошибок.** `http`, `network`, `invalid-response`, `timeout`, `aborted`. Сетевой этап обёрнут в отдельный `try/catch`, поэтому `ApiError` обработки ответа не превращается в `network`.

### 3.2. Доменный API

Файл `src/task-api.js`. Последний аргумент каждого метода данных — `{ signal }`.

| Метод | Запрос | Результат |
|---|---|---|
| `getTasks(filters)` | `GET /tasks` | `{ tasks, meta }` |
| `getTaskById(id)` | `GET /tasks/:id` | задача |
| `getCategories()` | `GET /categories` | массив категорий |
| `loadInitialData(filters)` | `GET /tasks` и `GET /categories` параллельно | `{ tasks, categories, meta }` |
| `createTask(draft)` | `POST /tasks` | созданная задача |
| `updateTask(id, changes)` | `PATCH /tasks/:id` | обновлённая задача |
| `setTaskCompleted(id, value)` | `PATCH /tasks/:id` с `{ completed }` | обновлённая задача |
| `deleteTask(id)` | `DELETE /tasks/:id` | `null` (ответ `204`) |
| `resetDemoData()` | `POST /debug/reset` без тела | `{ reset: true, total }` |

Схема ответа проверяется в самом доменном модуле, до передачи данных интерфейсу:

- каждая задача — функцией `isTask`, каждая категория — `isCategory`;
- коллекции — функцией `checkCollection` (массив `data`, уникальность `id`, `meta.total` равно длине `data`); для задач дополнительно `meta.filters` должен быть объектом;
- одиночная задача после `POST`/`PATCH`/`GET` — `isTask`, а для запросов по id ещё и совпадение `id`;
- ответ `DELETE` должен быть `null`, ответ сброса — `{ reset: true, total }`.

Неверные аргументы (неизвестный фильтр, `completed` не boolean, неверный `id`) отклоняются `TypeError` до отправки запроса. В `createTask` и `updateTask` из объекта берутся только допустимые поля, а значения не проверяются на клиенте повторно: ошибки значений возвращает сервер как `VALIDATION_ERROR`, а интерфейс проверяет форму заранее.

### 3.3. Состояния интерфейса

Файл `src/app-controller.js`. Контроллер хранит `tasks`, `categories`, `filters` и `editingId` и не обращается к `document`: весь вывод идёт через адаптер `view`.

- **`loading`.** Перед каждой загрузкой вызывается `setListState("loading")`, список скрывается, `aria-busy` становится `true`.
- **`ready` / `empty`.** После ответа выводятся задачи, обновляется счётчик `meta.total`. Если задач нет, состояние `empty`, а список очищается, чтобы старые карточки не оставались.
- **`error`.** При ошибке показывается сообщение из `messageForError` и кнопка «Повторить загрузку». Ошибка отменённого запроса (`aborted`) пользователю не показывается.
- **Повторная загрузка.** Пока категории не получены, повтор снова выполняет `loadInitialData` (задачи и категории). После первой успешной загрузки запрашиваются только задачи. Кнопка «Обновить» и смена фильтров запускают новую загрузку с текущими фильтрами.

### 3.4. Изменение данных

Любое изменение выполняется через общую функцию `mutate`.

1. Форма проверяется функцией `validateTaskDraft` (`src/form-validation.js`): название от 1 до 100 символов после `trim`, приоритет из `low`/`medium`/`high`, существующая категория (значение `select` приводится к числу). При ошибке запрос не отправляется, сообщения выводятся у полей, а у полей выставляется `aria-invalid`.
2. Пока выполняется запрос, вызывается `setMutationPending(true)` и кнопки блокируются; повторное действие в это время игнорируется.
3. Выполняется запрос: `createTask`, `updateTask` (если задан `editingId`), `setTaskCompleted` (новое значение противоположно текущему) или `deleteTask`. Сброс данных использует `resetDemoData`.
4. После успеха форма очищается и возвращается в режим создания, выводится сообщение об успехе, и список **повторно запрашивается у API** с текущими фильтрами. Локально список не правится, поэтому на экране всегда состояние сервера.
5. При ошибке выводится сообщение об ошибке, форма сохраняется. Ответ `404` дополнительно запускает обновление списка. Блокировка снимается в `finally`.

Карточки строятся в `src/task-view.js` только через `createElement` и `textContent`, поэтому текст вида `<img onerror=...>` отображается как текст.

### 3.5. Защита от устаревшего ответа

Для каждой загрузки создаётся новый `AbortController`, а предыдущий отменяется до начала новой загрузки (`abort()`). Отмена прерывает сам запрос на уровне `fetch`. Но отменить удаётся не всегда: ответ мог уже прийти и ждать обработки. Поэтому добавлена вторая защита: счётчик `loadSeq`, номер которого запоминается при старте загрузки. После `await` ответ применяется, только если запрос не отменён и его номер равен текущему. Иначе ответ молча отбрасывается и интерфейс не меняется. Ошибки отменённых запросов тоже не показываются.

### 5.2. Браузерные проверки

Страница `http://127.0.0.1:5506/checks.html`:


При первом прогоне прошли 12 из 14: сбоили проверки «Корректная форма создаёт задачу с серверным id» и «Ошибки формы не отправляют запрос и связаны с полями». Причина оказалась не в приложении, а во вспомогательной функции `waitFor` в `checks/browser.checks.js`. Условие `() => requireNode(doc, '[data-task-id="35"]')` бросает исключение при первом же опросе, пока ответ сервера ещё не пришёл, а `waitFor` его не перехватывала, и проверка падала мгновенно. Вторая проверка падала как следствие: запрос создания из первой завершался уже после сброса данных, и в списке оказывалось 13 задач вместо 12. Исправление: в `waitFor` вызов условия обёрнут в `try/catch`, исключение трактуется как «условие пока не выполнено», а опрос продолжается до тайм-аута. Остальной код проверок не менялся.

## 6. Ответы на контрольные вопросы

1. _Почему `fetch` не отклоняет Promise при ответе 404?_<br>
   Для `fetch` ответ 404 — это полноценный HTTP-ответ: сервер получил запрос и ответил. Promise отклоняется только когда ответа получить не удалось (нет соединения, отказ DNS, отмена, тайм-аут). Статус нужно проверять самостоятельно через `response.ok` или `response.status`, что и делает `requestJson`, превращая такой ответ в `ApiError` с `kind: "http"`.
2. _Почему ответ 204 нельзя разбирать вызовом `response.json()`?_<br>
   Статус 204 означает «нет содержимого», тело ответа пустое. Пустая строка не является корректным JSON, поэтому `response.json()` бросит `SyntaxError`. Клиент проверяет статус и возвращает `null`, не пытаясь читать тело. Так работает `DELETE`.
3. _Чем состояние `empty` отличается от `error`?_<br>
   `empty` — это успешный ответ сервера, в котором по выбранным условиям нет ни одной задачи; пользователю нужно изменить фильтры. `error` — запрос не удался (сеть, тайм-аут, HTTP-ошибка, неверный формат ответа); данных нет, потому что их не удалось получить, и нужно повторить загрузку. Поэтому у `error` есть кнопка повтора, а у `empty` её нет.
4. _Зачем отменять предыдущий запрос при смене фильтров?_<br>
   Ответы приходят в произвольном порядке: ответ на более старый запрос может прийти позже нового и перезаписать актуальный список. Отмена освобождает ресурсы и не даёт устаревшим данным попасть в интерфейс. Так как отмена может прийти слишком поздно, дополнительно проверяется номер загрузки.
5. _Почему после мутации список повторно запрашивается у API?_<br>
   Источник истины — сервер. Он назначает `id`, нормализует поля и применяет фильтры, а список мог измениться и по другим причинам. Если править список локально, интерфейс может разойтись с сервером (например, созданная задача не подходит под текущий фильтр). Повторный запрос с текущими фильтрами показывает фактическое состояние данных.

## 7. Вывод

Браузерный интерфейс не работает с данными напрямую, а получает их через цепочку: DOM-адаптер (`dom-app.js`), контроллер состояний (`app-controller.js`), доменный API (`task-api.js`) и общий HTTP-клиент (`api-client.js`). Каждый слой отвечает за своё: клиент знает про HTTP и виды ошибок, доменный слой — про контракт API и проверку схемы ответов, контроллер — про состояния и порядок действий, а адаптер — про разметку. Благодаря этому контроллер и клиент проверяются без браузера и без сети, на подставных `api`, `view` и `fetchFn`.

В ходе работы реализованы методы POST, PATCH и DELETE с корректной обработкой тела и ответа 204, состояния `loading`/`ready`/`empty`/`error`, повторное получение списка после изменений и защита от устаревших ответов (`AbortController` и номер загрузки). Найдена и исправлена ошибка во вспомогательной функции `waitFor` браузерных проверок (раздел 5.2), из-за которой корректная реализация создания задачи не проходила проверку. Итог: Node.js — 23 + 33 + 14 проверок, браузерные — 14 из 14, ручные сценарии и индивидуальный вариант 5 выполнены.
