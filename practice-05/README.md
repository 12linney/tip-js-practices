## Эксперимент с очередями выполнения

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, G, F | Сначала выполняется весь синхронный код: A, затем B (тело `async`-функции работает синхронно до первого `await`) и C. После этого стек пуст, и движок разбирает очередь микрозадач в порядке постановки: D, E, G. Таймер с задержкой `0` попадает в очередь макрозадач, поэтому F выполняется последним. |
| Фактический результат | A, B, C, D, E, G, F | Совпал с прогнозом. |

Фактический вывод `npm run example:order`:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: собственная микрозадача
F: задача таймера
```

- **Синхронный код:** A, B и C. Вызов `demonstrateAwait()` выполняет тело функции до `await null`, поэтому B выводится до C.
- **Микрозадачи:** D (обработчик `.then` уже готового Promise), E (продолжение после `await null`) и G (собственный `.then`, добавленный последним). Они выполняются в порядке постановки в очередь, после завершения синхронного кода.
- **Почему таймер с задержкой `0` не выполняется немедленно:** `setTimeout` не вызывает функцию сразу, а ставит её в очередь макрозадач. Цикл событий берёт следующую макрозадачу только после завершения текущего кода и полного опустошения очереди микрозадач, поэтому F идёт последним.
- **Изменится ли вывод при удалении обработчика Promise:** пропадёт только метка удалённого обработчика, порядок остальных не изменится. Например, без D получится A, B, C, E, G, F. Таймер в любом случае остаётся последним.

|---|---|---|
| URL запроса | `http://127.0.0.1:5505/api/tasks?completed=false&priority=high` | Ресурс `/tasks` с двумя фильтрами в query-строке |
| Метод | `GET` | Метод `fetch` по умолчанию: данные только читаются, не изменяются |

| `response.ok` | `true` | Статус входит в диапазон 200–299 |
| `Content-Type` | `application/json; charset=utf-8` | Тело ответа содержит JSON, его можно разобрать через `response.json()` |
| id полученных задач | `[4, 13, 34]` | Незавершённые задачи высокого приоритета |
| `meta.filters` | `{ completed: false, priority: 'high', categoryId: null, q: '' }` | Фильтры, которые сервер фактически применил |

| Запрос | Статус | Тело ответа |
|---|---|---|
| `GET /api/health` | `200 OK` | `{"data":{"status":"ok"}}` |
| `GET /api/tasks/25` | `200 OK` | `{"data":{"id":25,"title":"Исправить обработку ошибок","completed":true,"priority":"high","categoryId":2}}` |

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | Учебный HTTP-сервер: маршруты `/health`, `/tasks`, `/tasks/:id`, `/categories`, `/debug/*`, фильтрация, JSON-ошибки, CORS |
| `src/api-client.js` | Общий клиент: класс `ApiError`, `buildUrl`, `createApiClient` и `requestJson` (заголовки, тайм-аут, отмена, проверка статуса и `Content-Type`, разбор JSON) |
| `src/task-api.js` | Доменный слой: `getTasks`, `getTaskById`, `getCategories`, `loadInitialData`, проверка фильтров и схемы ответов |
| `src/variant.js` | Индивидуальный вариант: `variantNumber = 5`, `variantFilters = { categoryId: 1 }` |
| `src/main.js` | Точка входа: создаёт клиент, загружает данные, выводит таблицу задач и контрольную ошибку 404 |

**Почему `fetchFn` передаётся в `createApiClient`.** Клиент не привязан к глобальному `fetch`, поэтому в модульных проверках можно подставить имитацию и проверять код без реальной сети и сервера. В обычной работе по умолчанию используется `globalThis.fetch`.

**Почему HTTP-ошибки проверяются отдельно от сетевых.** `fetch` не отклоняет Promise при статусах 4xx и 5xx: он отклоняется только при сбое соединения, тайм-ауте или отмене. Поэтому статус нужно проверять через `response.ok`. Это разные ситуации. При HTTP-ошибке сервер ответил и сообщил причину (`status`, `code`, `details`), а при сетевой ошибке ответа нет вовсе. Реакция на них тоже разная.

**Почему JSON после разбора проверяется по контракту.** Корректный синтаксис JSON не гарантирует, что в нём нужные поля нужных типов. Сервер может вернуть другую структуру, повторяющиеся id или неверный `meta.total`. Проверка по контракту не даёт таким данным попасть дальше в приложение и превращает их в `ApiError` с видом `invalid-response`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | `parseBaseUrl` проверяет, что это непустая строка, абсолютный адрес со схемой `http` или `https`, без query и hash. Конечные слеши обрезаются, путь добавляется без двойного `//` | `check:client` №01, №04 |
| Кодирование query-параметров | Через `URL.searchParams.append`, без ручной склейки. Пропускаются только `undefined`, `null` и `""`, а `false` и `0` сохраняются | №02, №03 |
| Заголовок `Accept` | Отправляется `Accept: application/json`, метод `GET` | №05 |
| Проверка `response.ok` | При `!response.ok` создаётся `ApiError` с `kind: "http"`. Поля `status`, `code`, `details` берутся из `payload.error`, а при отсутствии тела сохраняется только статус | №08, №09 |
| Проверка `Content-Type` | Для успешного ответа требуется `application/json`, иначе `kind: "invalid-response"` | №10, интеграция №11 |
| Разбор JSON | `response.json()` вызывается в `try/catch`, при сбое выбрасывается `invalid-response` с сохранённым `cause` | №11, интеграция №10 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)`, по умолчанию 2000 мс. При срабатывании `kind: "timeout"` | №14, интеграция №12 |
| Внешняя отмена | Внешний `signal` объединяется с тайм-аутом через `AbortSignal.any`. По причине сигнала отличаются `aborted` и `timeout` | №15, интеграция №13 |

Пример результата `buildUrl` с кодированием кириллицы, пробела и спецсимволов, а также с сохранением `false` и `0`:

```text
http://127.0.0.1:5505/api/tasks?q=%D1%80%D0%B0%D0%B7%D0%BE%D0%B1%D1%80+promise+%26+%3F&completed=false&categoryId=0
```

## Доменный модуль задач

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id: 1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34 |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id: 4, 13, 34 |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | 1 — Учёба, 2 — Проект, 3 — Организация |
| `loadInitialData({ completed: false, priority: "high" })` | Объект `{ tasks, categories, meta }`: 3 задачи (id 4, 13, 34), 3 категории, `meta.total = 3`, `meta.filters = { completed: false, priority: "high", categoryId: null, q: "" }` |

Правила проверки:

- **Задача:** `id` — положительное целое число; `title` — строка длиной от 1 до 100 символов после `trim`; `completed` — boolean; `priority` — одно из `low`, `medium`, `high`; `categoryId` — положительное целое число.
- **Категория:** `id` — положительное целое число; `name` — строка длиной от 1 до 100 символов.
- **Уникальность id:** повторение id внутри `data` считается ошибкой `invalid-response`.
- **Поле `meta.total`:** должно совпадать с длиной массива `data`. Для задач дополнительно `meta.filters` должно быть объектом.
- **Фильтры:** допустимы только `completed` (boolean), `priority`, `categoryId` и `q` (строка до 100 символов, пустая строка
